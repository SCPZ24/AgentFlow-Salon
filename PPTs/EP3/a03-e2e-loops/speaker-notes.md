# A03 · 人机职责与 e2e 闭环｜讲者备注

主线约 7 分钟，异常分支约 4 分钟。四种协作模式保持同一个问题：修复空白姓名报名，并证明正常报名与弹窗重开未被破坏。不是严格的技术年代分期。

## 演示操作

加载后暂停。`→` / `Space` 前进，`←` 后退，`P` 重播本步，`R` 重置，`C` 打开或收起控制层，`Esc` 关闭控制层。阶段名称可以直接点击。

每步先定位 300ms，再移动 1000ms，落位呈现结果 500ms，随后停住。动画中再按前进，只完成本步。回退、跳阶段和重置直接显示完整状态；减少动效保留路径与结果。

控制层提供全屏与减少动效。默认遵循系统的减少动态效果设置；URL 中已有 `motion` 参数时优先使用 URL。刷新恢复 hash 状态。投影前在现场后排检查关键文字；本地静态帧不能证明真实投影效果。

静态备份由网页使用的同一份 SVG 场景直接导出，不是浏览器截图。页面本身无远程资源、后端和构建依赖。导出 PNG 的维护脚本需要开发环境中已有的 `sharp`，不影响 HTML 离线运行。

## 主线对照

| step | 讲解重点 |
|---|---|
| 0 | 比较工作方式，保持任务与验收不变。 人定义问题与边界，最终也由人判断。 |
| 1 | 人找到源码，粘贴给 Agent。 资料：人类 → Agent |
| 2 | Agent 生成候选代码，人复制到项目。 候选代码：Agent → 人类 |
| 3 | 人打开页面、运行检查。 执行器仍然是人：保存 → 运行 → 检查 |
| 4 | 人把错误再次贴回，Agent 才能继续。 反馈：人类 → Agent；搬运再次发生。 |
| 5 | 把目标、修改范围与验收写清楚。 目标：拒绝空白；范围：报名源码；验收：三项都满足。 |
| 6 | 更清楚的要求，产生更明确的候选。 源码仍需粘贴，修改仍需复制。 |
| 7 | 说明变好了，执行仍由人完成。 Prompt 本身没有创建文件权限、执行器或测试循环。 |
| 8 | 先选择这一轮真正需要的资料。 选入：项目规范、报名源码、错误输出。 |
| 9 | 选定工作流的读取工具，把材料送入上下文。 工具提供读取能力；Context 关注材料的选择与组织。 |
| 10 | 职责进入运行系统，人保留关键控制。 模型提出修改；工具应用修改；人保留范围与授权。 |
| 11 | Harness 执行允许范围内的修改。 执行 → 报名源码；受保护的验收基准保持不变。 |
| 12 | 检查发现：关闭后无法重新打开弹窗。 检查 → 失败反馈；不能把「已修改」当作成功。 |
| 13 | Agent 根据反馈修复；Harness 再执行。 失败反馈 → 修复请求 → 再执行 |
| 14 | 重新检查：三条验收条件均有证据。 空白被拒 ✓　有效成功 ✓　弹窗可重开 ✓ |
| 15 | 先交付小范围 diff。 候选修改：报名校验与弹窗状态复位。 |
| 16 | 附上测试结果，证明关键行为。 测试证据：空白 / 有效姓名 / 重开弹窗均通过。 |
| 17 | 补上界面复验，再交给人。 UI 复验：提交 → 关闭 → 重新打开。 |
| 18 | 候选交付完成，等待人类判断。 final 结束了回答；验收决定是否结束任务。 |
| 19 | 人类接受：这一轮 e2e 完成。 已接受 · 三条验收成立，修改范围可接受。 |
| 20 | 新约束回到目标澄清，外层 Loop 继续。 新增约束：全角空格也应拒绝；先澄清，再开始下一轮。 |

## 职责迁移

六个编号始终对应同一职责：01 定义目标、02 提供/取得资料、03 生成修改、04 执行与验证、05 失败处理、06 最终判断。卡片跨边界迁移时不改变身份和垂直顺序。

- ChatBox：人提供源码、复制修改、执行检查、搬运错误，模型输出候选文本。
- Prompt：把目标、范围、验收写清楚；不会自动获得执行器或创建验证闭环。
- Context：本例已有读取工具，强调按需选择材料。工具能力不是 Context 这个名称凭空赋予的。
- Harness：执行与验证进入运行系统；失败反馈回到模型决策，构成内部闭环。人仍保留目标、约束、授权和最终判断。

从步骤 9 顺序前进时，先到 `#step=10&sub=1`，只迁移“执行与验证”；再前进到 `#step=10&sub=0`，迁移“失败处理”。原有 `#step=10` 地址直接显示完整 Harness 阶段，保持旧链接语义。

证据仅在步骤 15–17 逐项交付。步骤 18 必须选择“接受”或“提出新约束”，前进键不会代替人类决定。步骤 19 的接受与步骤 20 的新约束分别保留在 hash 的 decision 字段中。

## 异常分支

在 Harness 阶段点击“演示异常”。拟修改的受保护文件为 `tests/acceptance.json`；允许修改的源码为 `src/registration.ts`。屏幕用短标签表达边界，详细路径在这里讲解。

- 步骤 0：测试失败：弹窗关闭后无法再次打开。 教学仿真 · 已有失败反馈，需要定位原因。
- 步骤 1：Agent 提议修改受保护的验收基准。 拟改 tests/acceptance.json，跳过「弹窗重开」检查。
- 步骤 2：Harness 拒绝越界动作，原文件保持不变。 拒绝原因：验收基准只读；允许修改 src/registration.ts。
- 步骤 3：Agent 已收到拒绝原因与失败反馈。 选择允许范围内修复，或在预算耗尽时上报。
- 步骤 4：回到允许范围，修复弹窗状态复位。 修复请求 → src/registration.ts；验收基准不变。
- 步骤 5：Harness 执行源码修改，再运行原有检查。 执行 → 检查；修复动作本身不等于成功。
- 步骤 6：原有检查通过，准备提交证据。 空白被拒 ✓　有效成功 ✓　弹窗可重开 ✓
- 步骤 7：预算耗尽：停止尝试，向人类上报。 已做：校验修改；未解：弹窗重开；需判断：范围与条件。
- 步骤 8：人类澄清条件，返回任务边界。 明确：重开后表单应清空；保留原验收基准。
- 步骤 9：人类授权一项具体的源码动作。 仅允许重置 src/registration.ts 的弹窗状态；不改验收基准。
- 步骤 10：Harness 按授权执行，并重新运行检查。 授权 → 执行 → 检查；授权不能直接变成成功。
- 步骤 11：检查通过，下一步交付证据供人验收。 源码动作已验证；最终接受仍在人类侧。
- 步骤 12：人类终止任务，系统停止执行。 已停止 · 保留已做事项与未解决问题。

在步骤 3 选择“范围内修复”或“停止并上报”；上报后的步骤 7 必须选择澄清、授权或终止。授权只能触发具体源码动作，仍需执行原检查并交付证据，不能直接成为成功。

该分支为教学仿真，不证明任何产品已经默认具备全部策略，也不是安全沙箱有效性证明。停止后保留已做事项和未解决问题。返回主线恢复 Harness 完整阶段。
