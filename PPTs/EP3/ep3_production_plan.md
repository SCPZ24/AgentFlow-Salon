# EP3 分享会策划案｜制作执行版

> 正式主题：AI赋能新时代软件工程——主流智能开发工具实战与趋势  
> 制作主线：从“让 Agent 改代码”，走向“组织并验收一次交付”  
> 本轮用途：指导后续 PPTX、HTML 小动画和实机演示素材制作；本文件不是已经制作完成的课件或已经跑通的演示。  
> 编写日期：2026-09-16

## 制作总说明

用“一份 PPTX + 多份 HTML 小动画 + 几个简单演示实例”构成分享。
本轮将其落实为：**20 个新增/细化的 PPT 页面说明（含导师 2 页和收尾 1 页）+ 3 个 HTML 动画 + 4 个主演示用例**。
### 90 分钟时间轴

为便于制作，暂按 90 分钟编排，并将导师时间计入总时长。上传草稿没有写出整场时长，因此以下分钟数属于制作排期假设，不是已确认的活动安排。

| 时间 | 环节 | 页面 / 媒体 | 现场目标 |
|---|---|---|---|
| 00:00–15:00 | 导师开场 | P01–P02 | 提出 AI 使用现象与“能力是否同步成长”的问题 |
| 15:00–18:00 | 接棒与目标 | P03 | 明确今天不再教启动工具，而是教如何组织一次交付 |
| 18:00–26:00 | 前置内容 | P04–P06；A01 | 看懂一次调用、工具执行与上下文更新 |
| 26:00–36:00 | Codex | P07–P10；D01–D02 | 看见批注修改和真实界面验收 |
| 36:00–56:00 | Pi | P11–P15；D03–D04；A02 | 看见最小内核、定制点和上下文拼装 |
| 56:00–72:00 | 智能开发工具趋势 | P16–P19；A03 | 看懂内外两层 Loop 与人机职责变化 |
| 72:00–85:00 | AI/CS学习路线 | 已定档内容 | 原案照讲，本轮不介入内容 |
| 85:00–90:00 | 收尾 / 问答 | P20 | 给出当晚就能做的一次工作流改进 |

导师只讲 10 分钟时，多出的 5 分钟留给互动或演示讲解，不临时增加新功能。导师超时，先压缩插件彩蛋和趋势扩展；不要靠删掉演示验收、跳过第三节或超速播放动画追回时间。

### 三种媒介各自负责什么

**PPT 负责结论和路标。** 一页只承担一个判断；屏幕上放结论、对比与证据，不把本策划案的讲稿整段粘上去。

**HTML 负责状态变化。** 只有需要“看到东西如何移动、增减、切换职责”的内容才做动画。三个动画都由讲者手动推进，不自动替讲者讲课。

**实机负责证明。** 证明某项能力确实发生过：批注传入了任务、文件真的变了、工具真的被调用、测试真的运行、页面真的被再次操作。模型说“完成”不算证据。

### 投影与视觉约定

PPT 使用 16:9。建议浅暖灰底、深色字，Agent/模型用青蓝，Harness 用琥珀，人类用紫色，失败用红色，验收通过用绿色。颜色必须配文字标签，不能只凭颜色辨认。无需寻找人物照片或堆工具 Logo，主视觉来自页面对比、上下文卡片和责任分工。

PPT 标题建议 32–40 pt，正文 24–28 pt，代码只保留能看清的短片段。HTML 在 1920×1080 和 1366×768 两档检查，正文不小于 22 CSS px；分屏终端建议 22–24 pt。不要把 API JSON、完整 system prompt、全屏 Git diff 缩成后排看不见的纹理。

Ghostty 的透明效果只做短暂展示。正式讲代码和日志时切到高对比、低透明或不透明的讲座主题；“自己桌面好看”不能优先于投影可读。

## 留给导师的前15分钟

### 原案锚点

导师自行发挥 10–15 分钟，只需要两页 PPT，主题是学生普遍用 AI 帮助编程的现象，以及这个现象带来的弊端。

原案还包含讲者与字节学长交流的个人见闻。这个材料可以用于接棒，但必须保留“我接触到的团队/学长的观察”的样本边界，不能变成“字节所有团队的正式政策”，也不能据此做行业使用率图表。

### P01｜AI在手，软件工程专业学生和业余VibeCoder的壁垒是？

**预算：7 分钟，导师主讲。**

**屏幕文案：**

> AI在手，软件工程专业学生和业余VibeCoder的壁垒是？

下面只放死句话：
“我有Codex，不懂编程的人也有Codex。”
“大家都可以向神(Astra)许愿”
“程序员的工作已经没有壁垒”
“计算机已死”

**导师展开方向：** 可以肯定 AI 的帮助，再讨论使用过程是否留下了理解、判断和复盘。不要将“使用 AI”本身定义成学习失败，也不要把使用时长直接当成能力高低的证据。

### P02｜工具可以提速，但是别被宠坏

**预算：8 分钟，导师主讲；最后约 30 秒交棒。**

**屏幕文案：**

> 工具可以提速，但是别被宠坏。

**画面：** 左侧三张工作卡：“生成实现”“执行命令”“整理说明”；右侧三张责任卡：“明确目标”“识别错误”“判断是否满足需求”。中间不是一道永久不可跨越的墙，而是标有“授权与验证”的连接带，避免暗示人类永远必须逐行手写或逐步操作。

**导师展开方向：** 用自己熟悉的课程或项目例子讲“看起来完成”和“真正完成”的差别。评价学生能力时，保留解释、修改、验收环节，而不只看一次生成的作品。

**讲者接棒建议：**

> “我和一位在字节工作的学长交流时，他接触到的团队已经在重度使用 Agent，审查方式也有差异。这只是个人交流的观察，不代表整个公司的统一规定。它让我更在意一个问题：大家都会用之后，我们的差异体现在哪里？”

> “接下来不重复‘怎么启动 Agent’，而是看两件事：一个集成工具如何完成修改与验收；一个极简工具如何被你组织成自己的工作流。”

不把这个见闻写成导师必须背书的结论。导师对案例不熟悉时，由讲者在 P03 口头补充即可。

## 智能开发工具实战

### P03｜今天从“会使用”往前走一步

**预算：3 分钟。**

**屏幕文案：**

> 让它改 → 让它看懂 → 让它执行 → 知道它有没有做好

**画面：** 四个横向阶段。只把“让它改”标为听众已有经验，其余三个是今天的增量。底部放 Codex 与 Pi 两张卡，分别写“集成工作流”和“可定制运行时”。

**过渡：** “先拆开一次调用，再看工具的成品体验。”

### 前置内容

保留原案的两项：LLM API 输入输出，以及 ReAct Loop。这里不讲网络请求 schema、字段拼写、采样参数、token 定价或 provider 兼容性；系统提示词如何拼装留给 Pi。

#### P04｜一次 LLM 调用，看见什么，交出什么？

**预算：3 分钟。**

**屏幕文案：**

> 模型接收本次上下文，输出回答或行动请求。

**画面：** 左侧四个输入格：“规则”“当前任务与历史”“工具说明”“已经获取的文件/页面/工具结果”；中间一个 LLM 方框；右侧两条出口：“面向用户的回答”“交给运行时的工具调用”。

**讲述边界：**

- 本场用“模型可见的有效上下文”作逻辑模型，不宣称所有 API 都让客户端每次按同一种格式重发完整历史。
- 项目文件在磁盘上，不等于文件正文已经在上下文里；读取、检索、附件处理等步骤决定哪些内容进入这一轮。
- 工具说明告诉模型可以请求什么，工具实现负责实际做事；两者不是同一个东西。
- 以本场客户端执行的读文件/改文件工具为例，模型产出调用请求，Harness 执行并回传结果；不要把这个简化说法推广成“所有平台内置工具都由本机执行”。

**核验说明：** OpenAI 的 function calling 文档明确区分模型返回调用、应用执行、结果送回模型及后续回答/调用。此处借它解释通用工程过程，不要求学生记忆 OpenAI 的字段。[^S01]

**过渡：** “一次调用不会自己长出循环；循环由外面的程序组织。”

#### P05｜它为什么能连续读文件、修改、运行测试？

**预算：4 分钟；切 A01。**

**屏幕文案：**

> Action 改变环境，Observation 改变下一轮输入。

PPT 留一张 A01 的完整静态帧，动画失败时仍能讲完。讲者用动画带大家经历一次“余票文案修复”。

#### A01｜ReAct Loop 与上下文增长

**文件：** `animations/a01-react-loop.html`  
**用途：** 让观众看懂每次 LLM 推理启动前有哪些输入，工具结果如何回到下一轮。  
**演示方式：** 默认暂停；右方向键或点击“下一步”推进。主线约 3 分钟，失败分支约 30 秒。

**固定布局：**

左侧是“本次模型可见上下文”，中间是“LLM / Harness”，右侧是“项目环境”；上下文侧优先给 messages 与累计工具结果留出空间。调用编号位于右上角，底部为紧凑阶段进度。Harness 必须有独立实体，不能把“模型输出”直接连到磁盘。

上下文面板的顶层分为 `system_prompt`、`tools`、`messages` 三栏。这里只是教学分组，不是真实 API schema。`thinking` 显示在 LLM 工作区；`tool`、`observation` 与 `final` 用不同卡片显示。

| 状态 | 屏幕变化 | 讲者说明 |
|---|---|---|
| A01-0 任务到来 | 出现用户任务：“余票为 0 时显示已满员” | 今天沿用一个很小的任务，避免业务分散注意力 |
| A01-1 Call 1 输入冻结 | 高亮规则、工具目录、用户消息；右侧磁盘文件仍灰色 | 模型此时还没读到函数正文 |
| A01-2 模型决策 | LLM 出现 `thinking（概念示意）` 状态，随后产出 `read` 调用卡 | 思考是本次推理中的过程，不额外画成一次 API 调用 |
| A01-3 Harness 执行 | 调用卡进入 Harness，再指向 `src/seat-label.ts` | 运行时接收请求，执行读取 |
| A01-4 Observation 返回 | 文件摘要变成工具结果，与对应调用一起加入历史 | 读取结果成为下一轮的证据；不是文件自己飞进模型 |
| A01-5 Call 2 与修改 | 新一轮输入高亮；模型请求 `edit`；环境出现 diff | 新输出依赖已取得的代码，而不是神秘地知道仓库 |
| A01-6 修改结果回传 | 出现“已应用修改”的工具结果 | “编辑成功”只证明文件改了，不证明业务正确 |
| A01-7 Call 3 与测试 | 模型请求 `bash: npm run test:seats`；Harness 执行 | 把验收条件变成可运行的反馈 |
| A01-8 Call 4 与回答 | 测试输出进入历史；模型给出 `final` | 主线共四次模型调用；工具执行不另外计成 LLM 调用 |
| A01-9 外部验收 | `final` 停在“候选交付”；人类验收章仍未盖下 | 本轮回答结束，不自动等于用户目标已验收 |

**失败分支 F：** 在 A01-8 前点击“测试失败”。返回一个红色测试结果卡，显示它进入下一轮上下文；箭头回到“定位/修复”，而不是直接转成成功。只表现“收到失败 → 再决策”的结构，不编造某模型的真实推理日志。

**上下文快照规则：** 每次请求开始时，显示当轮快照；本轮生成中的内容不能提前出现在本轮输入。历史工具调用与结果保留关联。动画可将已完成轮次折叠成“历史 1/2/3”，但折叠是显示处理，不暗示真实系统已做压缩。

**`thinking` 的边界：** 本动画展示教学示意，不是抓取模型内部完整思维链。不同模型/API 对 reasoning、摘要或不透明状态的处理不同；不得演成“所有模型都会公开一段 thinking，客户端再把原文全部塞回去”。[^S02]

**学术口径：** 原始 ReAct 研究强调推理、行动与环境观察的交替；现代工具调用 Harness 可能采用不同的消息结构。本动画是受 ReAct 启发的执行闭环示意，不宣称复刻某篇论文或某一产品的全部内部实现。[^S03]

**验收：** 观众在 A01-5 暂停时，应能回答：“这次比上次多看到了什么？”在 A01-6 暂停时，应能指出：“文件改了，但测试还没运行。”

#### P06｜用三个问题检查任何 Agent

**预算：1 分钟。**

屏幕只放三句：“这一轮看到了什么？”“通过什么工具行动？”“凭什么继续或结束？”

用一句话引入 Harness：“本场把模型之外，负责上下文、工具执行和循环控制的运行时组织层称作 Harness。”这是教学工作定义，不要求各产品用完全相同的命名。

过渡到 Codex：“先看一套已经把这些环节集成起来的体验。”

### Codex

#### 原案锚点与制作口径

原案提出两个候选：“最强的 computer use”和“在 web 上 annotation 来改前端”。本轮保留这两条演示方向，但不在正式课件上使用未经同条件比较证明的“最强”或“别家都没有”。

**核验说明：** 官方资料确认桌面工作流具有页面批注、样式反馈和 Computer Use 能力；当前使用入口、地区、工作区策略与权限仍应以讲者设备为准。页面批注属于桌面浏览器体验，不能用 CLI 的功能页替代验收。当前文档以 ChatGPT 桌面应用中的 Codex 工作流描述相关能力，PPT 上的产品名称和截图跟随彩排设备，不沿用旧截图猜入口。[^S04][^S05][^S06]

#### P07｜Codex：把“指哪里改哪里”接到交付闭环

**预算：1 分钟。**

屏幕放四步：“指出目标 → 修改实现 → 操作页面 → 检查结果”。右上角注明“本场展示桌面工作流”。

讲述重点不是模型名字、版本榜单或让它新建整个网站，而是反馈如何变成任务、实际界面如何变成验证证据。

过渡：“第一项，人把问题指准确；第二项，Agent 自己去复现与检查。”

#### P08｜不要只说“改好看”，把反馈钉在具体位置

**预算：4 分钟；主演示 D01。**

PPT 显示修改前/目标后两张等尺寸截图，中间预留一个批注标记。目标后截图必须来自彩排真实结果，不能用理想设计图冒充实际产物。

**屏幕结论：** “减少指代歧义，比把提示词写得更长更重要。”这是本场对演示的分析，不作为普遍量化结论。

#### D01｜用网页批注收敛首屏与主按钮

**证明目标：** 观众能看到选中的具体区域、发送给 Agent 的反馈、实际代码改动以及修改后的页面。

**起点：** Campus Day 的 V 问题版本。开发服务已经启动，Codex 已选择正确项目；内置浏览器打开本地页面。预置浏览器内容视口为 1280×800，用于固定前后比较，不要求现场拖动窗口精确量尺寸。

**现场动作：**

1. 用约 10 秒展示“留白过大、主按钮不在首屏”的问题。
2. 开启 Annotation，选中首屏活动介绍区域，留下第一条批注。
3. 再选中按钮组，留下第二条批注；展示批注随任务一起发送的状态。
4. 发送总指令；有可讲的 diff 或页面变化时解释，没有进展时按统一超时规则切录屏。
5. 刷新真实页面，检查首屏，再点一次报名按钮确认入口没有被样式改坏。

**批注文本：**

```text
批注 1，选中首屏介绍区域：
这块上下留白太大。保留现有标题、时间地点和议程文案，
让“立即报名”在当前 1280×800 内容视口的首屏中完整可见。
不要靠缩小正文字号来塞内容，不要改动下方三个议程卡片。

批注 2，选中按钮组：
“立即报名”是唯一主操作，请让它明显区别于“查看议程”。
后者改为次级视觉层级，保留两个按钮现有的行为。
```

**总指令：**

```text
处理这两条页面批注，仅调整对应区域的样式与必要结构。
不要新增依赖、不要改活动内容、不要修改表单逻辑和测试。
完成后重新查看页面，并简要报告修改了哪些文件、检查了什么。
```

**验收标准：** 同一视口下主按钮完整可见；主次按钮有明确区分；议程文案未变；点击主按钮仍能打开报名弹窗；检查改动文件清单，没有无关重构。演示不以“我觉得更漂亮了”作为唯一标准。

**讲解问题：** “刚才比一句‘改好看’多传进去了什么？”引导学生指出目标区域、结果约束、不能动的范围。

**范围控制：** 不现场展示所有高级样式调节功能。官方支持更细的样式反馈，但本演示只保留两条足够明显的批注，避免变成设计面板教学。[^S04]

**失败退路：** 批注入口不可用时，直接使用标注为“彩排录屏”的片段展示批注流程；不要改成手工贴图后还说是原生 Annotation。代码修改耗时超预算时，先停止当前任务，再展示彩排 diff 和结果；口头说明当前实时任务未完成。

**必须提前录制：** 选区域并批注、发送反馈、出现代码变化、刷新并点击按钮四个阶段；另外保存完整未剪辑素材用于核对。

#### P09｜写完不是结束，让 Agent 把操作再走一遍

**预算：4 分钟；主演示 D02。**

屏幕放一个“操作 → 失败证据 → 修复 → 相同操作复验”的环。重点镜头是鼠标/输入和页面状态变化，不是长篇聊天输出。

#### D02｜Computer Use 复现空白姓名问题并复验

**证明目标：** 图形界面的真实操作参与了复现与验收，而不是仅凭模型描述“应该没问题”。

#### A02｜Pi 上下文装配台

**文件：** `animations/a02-pi-context.html`  
**用途：** 解释系统提示词的来源、工具与对话的独立位置，以及按需加载。  
**演示方式：** 8 个手动状态，约 5 分钟；最后用 1 分钟提问。

**固定布局：** 左侧约 30% 为“资源来源”，中间约 15% 为紧凑的 Harness 装配接点，右侧约 55% 为“本次请求的逻辑结构”。右侧始终有 `system_prompt`、`tools`、`messages` 三个独立盒子。下方另设“不发送给模型的本地状态”栏。

| 状态 | 演出内容 | 本页必须讲清楚 |
|---|---|---|
| A02-0 来源出现 | 左侧出现默认规则、AGENTS.md、skills、模板、扩展、主题、会话 | 材料来源不等于最终消息类型 |
| A02-1 默认系统提示词 | 默认身份/规则、工具简述等形成基础块 | 默认文本来自 Harness，而不是每次由用户手写 |
| A02-2 系统补充 | `APPEND_SYSTEM.md`、加载到的项目说明、skill 目录信息、cwd 分别入位 | 只表现已核验的来源；不自行加一个“全仓库正文”块 |
| A02-3 自定义分支 | 点击 `SYSTEM.md`，只替换默认基础块，后续上下文块仍保留 | 当前构建函数的自定义分支不等于清空其他上下文 |
| A02-4 工具目录 | 活跃工具定义进入 `tools`；简述可能也出现在系统规则中 | 工具 schema/定义与提示词里的介绍不能画成同一个数据对象 |
| A02-5 模板与历史 | 用户命令展开的提示词进入消息；当前会话分支形成历史 | Prompt template 通常展开为用户请求，不是自动获得 system 级别 |
| A02-6 按需读取 skill | 先有技能名称/描述；收到相关任务后读取一个 SKILL.md，正文进入消息/工具结果路径 | “列在目录里”和“全文已经读到”不是一回事 |
| A02-7 运行与整理 | 工具结果追加；老历史可被摘要替代，近期上下文保留；主题停在本地栏 | 扩展可能改变模型输入，也可能只改 UI；压缩不等于改变模型权重 |

**系统提示词的制作细节：** 当前 `buildSystemPrompt` 的默认分支会组织基础说明、可见工具简述与规则，再追加补充提示、项目上下文、满足条件的 skills 信息以及工作目录。自定义基础提示词分支仍会追加相应项目/技能/目录内容。动画按本次读取的源码组织，不把某个拼接顺序宣称成所有版本永久不变的协议。[^S13]

**项目规则的制作细节：** 只展示全局和当前项目两个 AGENTS 示例，避免在舞台上展开所有祖先目录和覆盖规则。补充说明：实际来源与覆盖策略由当前版本资源加载器决定；规则文件是模型指令，不是天然的文件系统权限屏障。[^S07]

**技能的制作细节：** 默认发现流程先暴露名称/描述等目录信息，匹配任务后再读正文；显式 `/skill:name` 有主动加载入口。不要把技能全部正文一开场就塞进 system，也不要保证模型永远能自动选对 skill。[^S14]

**两组可切换样本：**

| 样本 | 规则 / 输入 | 用途 |
|---|---|---|
| 精简、相关 | “只修改目标源文件；保持现有风格；运行 test:seats；不得放宽测试” | 显示与本轮小任务直接相关的约束 |
| 冗长、冲突 | 旧项目框架说明、过期命令、大量无关日志，再混入本轮需求 | 显示需要筛选的材料，不宣称存在一个普适 token 阈值 |

这些样本是教学构造，不是实测性能数据。若要显示 token 数，必须来自固定 provider/tokenizer 的实际计数；默认只用相对长度，不写看似精确的估值。

**动效规则：** 来源卡复制成内容块后，来源仍保留在左侧，避免暗示文件被移动/删除。更改主题只让本地 UI 栏变化，右侧上下文不得跟着无理由变长。上下文压缩只作用于示意的历史材料，不让整个 system prompt 突然变成一段聊天摘要。

**互动问题：** “一套主题会不会必然占据模型上下文？”“一个 skill 出现在目录里，是否说明正文已加载？”“AGENTS.md 写不能动某文件，和运行时拦截访问，是同一件事吗？”

**收束句：** “上下文工程不是把更多东西塞进去，而是让这一轮拿到需要的信息。”这是对本动画的总结；相关性、按需读取和长任务上下文整理也有公开工程实践支持。[^S15]

## 智能开发工具趋势

### 原案锚点

保留原案的定义：一个问题从确定到解决、直到验收完成的过程，称为一次 e2e（end to end）。人和 AI 通过多轮交互完成它，形成外层协作 Loop；这个 Loop 与前面介绍的 ReAct Loop 不同。

保留原案要求的左右分屏：**左侧 Agent 职责，右侧人类职责**。保留 ChatBox、Prompt Engineering、Context Engineering、Harness Engineering 四个阶段名称。

**讲述限定：** 四阶段是本场解释“关注点与职责如何变化”的教学模型，不是严格的行业史分期、标准术语体系或互相淘汰的四代产品。它们在现实工作流中可以共存；不硬标“某年之后人人都进入某时代”。

### P16｜两个 Loop，别混成一个

**预算：2 分钟。**

**画面：** 外圈“人提出目标 → Agent 交付 → 人检查与反馈 → 再交付”；其中“Agent 交付”内部嵌一个较小的“推理 → 工具 → 观察 → 再推理”。

**屏幕文案：**

> 内层：下一步怎么做？  
> 外层：做到什么，算真正完成？

**讲述例子：** D02 里，读源码、编辑、测试可以发生在 Agent 的内部循环；讲者先提出“空白姓名不能成功”，再判断结果是否满足要求，属于外层协作。一次人类消息可以触发多次工具调用，二者不一一对应。

**过渡：** “接下来的‘时代变化’，看的是外层人机分工，不是模型内部循环多了几个箭头。”

### P17｜同一个任务，在四种协作方式里怎么完成？

**预算：7 分钟；切 A03 的四阶段主线。**

PPT 放四个阶段名和一句问题：“哪些动作从人手里移到了系统里，哪些判断仍需要人？”不再开一个全新的例子。

### A03｜一次 e2e 的人机职责迁移

**文件：** `animations/a03-e2e-loops.html`  
**用途：** 看见人类、Agent 与 Harness 如何共同完成同一个任务。  
**演示方式：** 四阶段 + 一个异常分支；不自动轮播。P17 讲主线，P18 复用异常分支，不制作第四个 HTML。

**固定问题：** “修复 Campus Day 空白姓名也能报名的问题，并证明没有破坏正常报名。”

**固定布局：** 左侧 55% 是 Agent 职责侧，右侧 45% 是人类职责侧。左侧内部另有一个细边框区域标注“Harness / 工具 / 检查”，避免把脚本、测试和权限机制都画成模型脑内能力。顶端固定目标与验收条件，底部固定“候选结果 → 证据 → 验收”的状态条。

六类任务使用固定 ID，切阶段时同一张卡移动而不是换一套图标：定义目标、提供/取得资料、生成修改、执行与验证、失败处理、最终判断。人类侧的目标、关键取舍与授权不能在最后一幕凭空消失。

| 阶段 | Agent / 系统侧 | 人类侧 | 动画应该表达什么 |
|---|---|---|---|
| ChatBox | 根据粘贴的内容解释、生成候选代码 | 找文件、粘贴、复制修改、运行页面、把错误再贴回去、验收 | 大量跨边界搬运；AI 主要交付文本 |
| Prompt Engineering | 在更明确的任务、边界、输出格式下生成候选结果 | 花心思写清要求，仍主要自己搬运与执行 | 问法改善了，但不会自动得到文件权限、执行器或测试循环 |
| Context Engineering | 在本场选定的带工具工作流中，按需取得项目规范、源码、日志，再行动 | 整理可靠来源、定义要提供什么、检查信息缺口与结果 | 重点从“这句话怎么写”扩展到“这一轮看到了什么”；工具执行能力不是 Context Engineering 这个名词凭空赋予的 |
| Harness Engineering | 上下文加载、执行、检查、失败重试、状态记录、异常上报由运行系统协同组织 | 定义目标与不可破坏的约束，做必要审批、处理歧义、接受或拒绝结果 | 更多可验证的过程在系统内闭合，人保留关键判断和控制入口 |

**逐步分镜：**

| 状态 | 动作 | 讲者台词要点 |
|---|---|---|
| A03-0 固定目标 | 顶部出现同一任务与三条验收条件 | 比较工作方式，不靠更换难度制造进步感 |
| A03-1 ChatBox | 资料与代码包反复跨越中线；人按下“运行” | 人在担任文件搬运、执行器和反馈中转站 |
| A03-2 Prompt | 人类需求卡展开为目标/范围/验收；搬运箭头仍保留 | 更好的说明很重要，但它没有自动创建执行闭环 |
| A03-3 Context | 规范、代码、错误输出沿明确路径进入左侧；无关资料留在外面 | 把正确材料提供给正确的一轮 |
| A03-4 Harness | 左侧展开“执行 → 检查 → 失败反馈 → 再执行”；跨中线箭头集中到关键判断处 | 不是多写一段 system prompt，而是把过程变成运行系统 |
| A03-5 候选交付 | 出现 diff、测试、UI 复验三张证据卡，状态为“待验收” | 先拿证据，再接受结果 |
| A03-6 人类判断 | 讲者点击“接受”或“提出新约束”；拒绝时回到任务边界 | 外层 Loop 可以继续；并非任何 final 都结束 e2e |

**数量表达：** 可以显示当前示意图里经过了哪些步骤，但不写“效率提升 10 倍”“人类参与下降 80%”等未测数据。若显示箭头计数，必须注明“本图示意，不是实测指标”。默认不放计数器。

**不要偷换概念：** Prompt Engineering 与 Context Engineering 的区分在这里是关注对象的扩大，不是前者没有上下文；Harness 也不是把人删掉或无限增加插件。模型能力提升后，有些专门补丁可以被移除；需要继续保留的是当前任务真正需要的执行、反馈与边界。

**验收：** 在四种模式中，观众能找到同一个目标、同一个任务和最终的接受/拒绝入口；能分清哪些是 LLM 输出，哪些是普通程序执行。

### P18｜决定可用性的，往往是失败之后怎么办

**预算：4 分钟；使用 A03 异常分支。**

**屏幕文案：**

> 不只设计成功路径，还要设计停止、回退与上报。

**动画异常分支 A03-F：**

1. 执行测试后得到失败结果，左侧出现失败卡。
2. Agent 提出一个越界动作：改动受保护的验收基准文件，以便“让检查通过”。
3. Harness 的明确权限/路径策略拒绝该动作，返回“拒绝原因”，原文件保持不变。
4. Agent 收到拒绝与测试反馈，选择在允许范围内修复；若本次尝试预算耗尽，则提交“已做事项、未解决问题、需要人类判断的点”。
5. 人类侧出现一次真正有内容的介入：澄清验收条件、允许特定动作，或者终止任务；不是盲点“继续”。

这是教学仿真，用来说明运行系统该承担的职责，不声称当前 Codex、Pi 或刚才的插件已经默认实现全部策略。脚本中的“拒绝”也不能作为安全沙箱有效性的证明。真实强约束需要覆盖相关工具与执行入口，而不只是搜索一句危险命令或在 AGENTS.md 写一句禁止。

**讲者补充：** 除了错误，停止条件还可能来自预算、取消、权限不足和目标歧义。自主运行时间更长不是单独的成功标准；有价值的是能否交付满足条件的结果，以及出问题时能否定位和接管。

**趋势证据卡（约 40 秒）：** OpenAI 在 Harness engineering 的公开实践中描述了对工作环境、可读资料、界面/日志反馈与机械检查的投入。这里用它支撑“工程工作向环境和反馈系统扩展”的判断，不照搬其内部项目的效率数字，也不将单个组织的实践当成所有项目的默认解。[^S16]

### P19｜工程背景的差异化，落在什么东西上？

**预算：3 分钟。**

画面回到 Campus Day，用三组具体材料代替抽象口号：

| 能力 | 这次分享已经看过的实物 | 听众可以如何复用 |
|---|---|---|
| 定义与取舍 | 批注、范围约束、空白/有效姓名验收条件 | 把模糊要求变成可判断结果 |
| 组织与执行 | 工具接点、项目规则、按需加载、可运行命令 | 让 Agent 找得到材料、做得动事情 |
| 验证与接管 | 小 diff、测试日志、界面复验、异常上报 | 不只看“完成”，还能判断是否应接受 |

**讲述重点：** 不把差异化等同于“会写更多插件”或“装了最复杂的 Agent”。选择合适的成品工具、删掉无效约束、设计可靠检查，本身就是工程判断。没必要为了证明自己有技术而重写现成能力。

**过渡到第三节：**

> “前面这些判断不是靠记住几个提示词就能稳定做好的。它们背后仍然是编程、软件工程和对系统的理解。接下来进入已经准备好的 AI/CS 学习路线。”

第三节按原案讲授，不在这里增加新的课程推荐或改写既定学习顺序。

### HTML 动画统一交互契约

三个 HTML 是三个独立、可本地打开的教学动画，不搭建一个复杂的讲座后台。

| 交互 | 约定 |
|---|---|
| 默认状态 | 加载后暂停在第一帧，不自动播放 |

预先准备的测试应固定且可读。演示 Agent 可以修代码，但不能通过修改验收条件制造“全部通过”。用于观察的初始缺陷直接写在讲者说明里，不做“故意整蛊模型”的隐藏陷阱。

环境记录至少包括：操作系统、桌面应用版本、模型/provider 与配置、Pi 版本、Node 版本、插件版本/commit、浏览器、视口、已批准的权限范围。没有记录到的版本，不填猜测值。

### 避免观众等 AI 的节奏规则

以下是演出预算，不是对模型响应速度的承诺。

**每次提交前，先说清楚要看什么。** 观众要知道接下来盯批注、diff、鼠标还是测试结果，不能只看到一个光标闪烁。

**30 秒没有可讲的新进展，就准备切素材；60 秒仍未完成这一小步，停止任务并切彩排片段。** 思考指示器本身不算值得持续等待的进展。不要把一个小演示拖成几分钟的模型等待。

**可以在执行时解释刚才的机制，但不开始下一段需要操作同一工程的任务。** 避免两个 Agent 同时改同一文件、录屏播放时后台继续操作桌面、或者页面热更新到意料之外的状态。

彩排录屏固定标识“彩排录屏”；加速则标速度，删去了等待则说明删去了等待。演示本来就以可理解、可复现为目标，公开使用备用素材比伪装实时成功更可靠。

### 开演资格与失败切换

| 检查项 | 上台标准 | 不达标的处理 |
|---|---|---|
| D01–D03 重复运行 | 从同一快照至少连续三次达到指定验收条件；实时片段满足上述等待预算 | 用录屏作为主讲证据，现场只展示已验证的短操作 |
| D04 插件组合 | 实际宿主加载正常，UI 不重叠，工具调用成功 | 去掉未通过的实机片段，保留准确截图和说明 |
| 网络 | 模型服务与选定抓取站点在现场网络可访问 | 启用离线素材，不现场调网络 |
| 权限 | 操作目标应用可用，范围受控，无私人窗口 | 停止 GUI 操作，不临时开全权限 |
| HTML | 三个页面断网可开、可跳帧、无溢出 | 用关键帧/PPT 静态图 |

只有上台设备的真实彩排能确认演示通过。本轮已经确定用例与检查方法，但没有访问讲者本机，也没有执行 Codex/Pi 实机演示。

### 最终交付验收

PPT 验收关注“观众每页应带走哪一句话”，而不是是否复制了策划全文。HTML 验收关注“任一状态是否讲得通，是否能回退”，而不是动效数量。演示验收关注“操作与证据是否对得上”，而不是聊天窗口是否出现了完成字样。

制作时不能擅自增加第三款 Coding Agent、第四个动画、复杂后端、模型测评或新的学习路线。出现资料冲突时，保留本场教学意图，同时在备注中记录当前版本的实际行为，不能把未知能力写成已经实现。

## AI/CS学习路线

### 编程语言在AI时代的生态位

- Python：适合做实验/数学建模/脚本，用处最多，求职最广。建议会。
- TypeScript：适合做Agent产品与前端。
- C++：完成复杂、性能敏感的系统。可以配合CUDA写驱动GPU的LLM推理引擎。
- Rust：强调内存安全与性能控制。用于写高性能Agent Harness或者轻量工具。


### 计算机基础

可以不做笔记，但是一定要做Lab！

#### 入门
- CS61A：Python为主，通过函数、递归、数据抽象、面向对象等内容，训练如何组织程序、控制复杂度。最后Lab手写一个解释器。


#### 有意思的编程课
- CS61B：Java为主。包含两大块：Java与面向对象编程；数据结构。学完等于掌握本校大一下的面向对象程序设计和大二上的数据结构。最后要求学生自己动脑经实现一个“地图生成游戏”（课程给脚手架，学生往里面填充具体的算法）。
- MIT6.102：我正在学。TypeScript为主，讲解学校里不会教的软件工程的细节和习惯。


#### 数学强化
- MIT18.06：线性代数常青树。
- MIT6.041：足够硬核的概率论。

当代LLM推理架构一般是transformers。transformers里其实能找到大学数学的影子：
- 前向传播：线性代数/矩阵乘法
- 反向传播：偏导数、链式法则/高等数学；梯度、矩阵偏导：高数和线代大舞台。
- SoftMax/token采样：概率论


#### 机器学习

- MIT6.036：Python+numpy。比较难的“机器学习基础课”。适合数学好的同学，有挑战性。
- 吴恩达机器学习系列：Python+Pytorch。门槛低，更像科普。
- MIT6.S184：Python+Pytorch。AI图像生成精品小课。讲清楚用于图像生成的Flow/Diffusion模型原理，扩展到U-net/ViT。


#### 大语言模型数学原理与工程实践
- CS224N：Python+Pytorch进入自然语言处理的世界，讲清楚人类处理自然语言的各种工具和尝试，包括N-Gram，RNN，LSTM，Transformers等。Lab里有一个机器学习翻译器。
- CUDA Programming Course – High-Performance Computing with GPUs：从0学习CUDA语言。最后用CUDA实现一个多层感知器，用于手写数字识别。
- CMU11868：用C++和Python手写一个“小Pytorch”。现代LLM原理。3侧入手：
    1. 数学上讲清Transformers
    2. 把数学变成工程化引擎：数学的矩阵乘法在GPU的硬件上如何加速；CUDA语言/GEMM是什么？显存/计算谁是瓶颈？
    3. 推理加速：多卡协作（显存/计算/通信/流水线调度）；量化
